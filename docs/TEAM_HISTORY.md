# Team identity and history concordance

The project collects men's football. `providers/concordance/team_scope.json`
contains reviewed provider profiles that must be excluded. Explicit female
gender metadata or a women's-team label also prevents a team match. Exclusions
are scoped to team/provider IDs: an unrelated player with the same number is
unaffected. A mixed reference keeps its men's IDs, clears an excluded peer ID,
and remains a conflict for review. Raw source evidence remains available.

## The additional dataframe

`dataset/concordance/team_history.csv` is a separate team-only concordance. It is
generated by dataset ID exports, fixture builds, and Main's identity refresh.
Compiled fixture bundles and MSI dataset transfers carry it to Main. Main
regenerates it from the catalog shipped with its code, so an older worker cannot
erase a current history catalog. Match and player concordance schemas do not
change.

```python
import pandas as pd

history = pd.read_csv("dataset/concordance/team_history.csv",
                      dtype=str, keep_default_na=False)
```

Each row is one directed relationship. The columns include:

- `from_team_key`, `to_team_key`: stable project keys for the historical sporting
  entities or eras. A rename keeps the same key on both ends.
- `from_name`, `to_name`: the names for that particular transition.
- `relationship`: `renamed_to`, `succeeded_by`, `merged_into`, `split_into`,
  `transferred_rights_to`, or `distinct_from`.
- `event_id`: groups all parents of a merger, or all children of a split.
- `effective_date`, `effective_year`, `date_precision`: exact dates only when
  supported; a known year does not silently become January 1.
- `from_sofascore_id`, `from_fotmob_id`, `from_whoscored_id` and matching `to_`
  columns: native provider references, with unavailable/unverified IDs blank.
- `from_reep_id`, `to_reep_id`: filled only if the available native references
  resolve to one Reep entity. The corresponding `*_reep_ids` JSON arrays retain
  all candidates where Reep disagrees, rather than choosing one arbitrarily.
- `status`, `source_urls`, `notes`: research/review state and provenance.
- `gender=male`, `used_for_identity_matching=False`: this table is an analysis
  relationship layer, not permission to treat every connected team as identical.

The initial catalog records 25 relationships across 30 team eras from the eleven
researched reviews. They are marked `researched`; adding the history does not
approve the pending provider identity conflicts. Split relationships are
supported, but no unverified real-world split has been invented to fill the table.

## Using the links in analysis

Join native team IDs to the relevant endpoint to find predecessor/successor
relationships. Exclude blank IDs before joining. A merger or split is genuinely
one-to-many, so a history join may intentionally produce multiple rows. Filter
the relationship types and date/era you want; `distinct_from` is an exclusion,
not an ancestry edge. Do not follow rename self-links as ancestry edges.

Shared provider IDs can span eras, such as CA Bastia and Bastia-Borgo. The
relationship date supplies the boundary; an ID-only join cannot assign every
historical match to an era. Where only the year is known, matches in the boundary
year may still need review. An optional analytical club-history grouping may
combine successor eras without changing the team that played each match.

The team eras and relationships are reviewed data in
`providers/concordance/team_history.json`. Keep existing keys/relationship IDs
stable, add source URLs, and represent unknown dates/IDs as blanks. Actual
same-team alias decisions stay in `team_profiles.json`, independently of history.

## Reep and this project

Reep's public model has stable entities, provider/namespace bridges, aliases,
typed relationship edges, and duplicate-entity redirects. Its download page
lists succession and affiliation edges. A Reep ID redirect repairs duplicate
register identities; it is not a record of two different clubs merging.

The project's compact Reep index currently imports provider bridges and redirects,
not the complete relationship graph. The current `edges.csv.gz` release is about
222 MB compressed; this feature does not download that graph or require a hosted
API subscription. Reep IDs remain useful foreign keys alongside the independently
sourced, small project history catalog. Review decisions and known exclusions
remain stronger than an upstream bridge.

The reader supports both legacy Reep release pointers/checksums and the new
checksum-pinned release manifest with object paths. Existing bulk files are
still temporary and checksum-verified; no full Reep refresh is needed to export
team history.
